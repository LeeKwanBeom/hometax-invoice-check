# 정기 점검표 (hometax-invoice-check)

이 파일이 점검 절차의 정본이다. 매 회차 끝에 "점검표 개정안"에서 사용자가 채택한 것만 반영하고, audit/last-audit.md 와 같은 push 로 올린다. 둘 중 하나만 갱신하면 다음 회차에 어긋난다. 채택 여부를 묻기 전에 고치지 마라. 버전: 6차 정기점검 · 2026-09-07 (저장소로 이관한 첫 회차. 이번 회차 개정안은 아직 반영하지 않았다 — 사용자 채택 대기)

[시작 전 확인 — 실 데이터가 있으면 그걸로]
이 스킬은 tests/fixtures/ 의 홈택스 파일 6개만으로도 점검이 가능하다. 다만 fixtures는 고정된 과거 데이터라, 아래 항목은 실 데이터가 있어야 판정된다: 당월 기준 월 컬럼 생성, 발급기한 임박 판정, 신규 거래처·사업자번호 변경 감지, 홈택스 다운로드 형식 변경(컬럼명·헤더 행·인코딩).
업로드된 파일부터 확인해라. 최근 홈택스 매입 목록 xls가 올라와 있으면 fixtures와 함께 둘 다 돌리고, 결과가 다르면 그 차이를 반드시 보고해라. 없으면 fixtures로만 진행하되, 위 항목은 전부 [추론]으로 표시하고 기준선의 "점검 대상" 줄에 실 데이터 없음 — fixtures만 사용 이라고 남겨라. 없는 데이터를 지어내거나 fixtures 값을 실 데이터인 것처럼 쓰지 마라.

[운영 조건]
실행 빈도: 월 1~2회. 주로 월초, 전월분 발급기한(익월 10일) 전후
실행자: 나 혼자, 수동 실행
정본은 전부 GitHub 저장소(LeeKwanBeom/hometax-invoice-check, Public)에 있다. push.py --code 로 반영한다.
설치본 SKILL.md(/mnt/skills/plugins/hometax-invoice-check/SKILL.md)는 55행짜리 얇은 부트스트랩이다. 저장소를 받아 오라는 안내만 들어 있고 절차·명령어·옵션·등급 이름은 없다. 그 원본은 저장소 install/SKILL.md 다.
설치 경로는 세션마다 패키지에서 다시 풀린다. 쓰기는 되지만 보존되지 않는다. 여기 쓴 건 전부 임시다. 남겨야 할 건 반드시 저장소로 push 할 것. 부트스트랩 문구 자체를 바꾸려면 저장소 install/SKILL.md 를 고쳐 push 한 뒤, 내가 Claude 설정에서 스킬을 재업로드해야 실제로 반영된다.

[실물을 봐줘. SKILL.md 설명만 읽고 판단하지 마]
네가 "못 한다" 또는 "그런 건 없다"고 답할 거면, 그전에 실제로 시도하거나 찾아본 결과를 같이 보여줘. 확인 안 했으면 확인 안 했다고 말해줘.

1. 저장소 실물을 받아서 확인
   curl -sL https://codeload.github.com/LeeKwanBeom/hometax-invoice-check/tar.gz/refs/heads/main | tar xz --strip-components=1
   (raw.githubusercontent.com 은 5분 캐시라 쓰지 말 것)

   대상 파일 전체: SKILL.md(정본) / install/SKILL.md(부트스트랩 원본) / README.md / sync.py
   config/check-config.json / config/vendors.json
   references/column-mapping.md / judgment-rules.md / excel-format.md
   scripts/common.py / check_input.py / build_report.py / validate.py / push.py
   state/last-run.json / tests/test_edge_cases.py
   audit/last-audit.md

   실제 ls 결과가 이 목록과 다르면 그것부터 알려줄 것. 행수는 회차마다 바뀌므로 목록에 적지 않는다. 실제 값을 기준선에 기록해라.

2. 샘플로 실제 1회 실행해서 산출물 xlsx를 직접 열어볼 것
   tests/fixtures/ 의 홈택스 파일 6개를 쓰면 된다. 코드만 읽지 말고 돌려서 나온 xlsx를 openpyxl로 열어 확인해야 함. 이 스킬은 산출물이 매번 새로 생성되는 구조라 "배포본" 대신 이게 실물이다. xlrd 가 없으면 pip install xlrd --break-system-packages 로 넣고 진행한다.

3. 세 파일이 서로 맞는지 대조할 것
   (a) 지금 이 대화에서 읽히는 설치본 SKILL.md (얇은 부트스트랩)
   (b) 저장소 install/SKILL.md (그 원본)
   (c) 저장소 SKILL.md (실제 설명서 정본)
   (a)와 (b)가 다르면 (b)가 최신이고, 내가 재업로드를 안 한 것이다. md5를 찍어 알려줄 것. (a)에 절차·명령어·옵션·등급 이름이 다시 들어가 있으면 그 자체가 결함이다. 얇게 유지하는 게 이 구조의 핵심이다.

[0단계 — 기준선 대조. 신규 진단보다 이걸 먼저]
1)에서 받은 저장소의 audit/last-audit.md 를 먼저 읽어라. 이게 정본이다. 설치 경로에도 사본이 있을 수 있지만 세션 간 보존이 안 되므로 믿지 마라. 저장소에 없으면 "기준선 파일 없음"이라고 명시하고 (2)로 넘어가라.

(1) 거기 적힌 항목을 지금 실물에서 하나씩 다시 확인해라. 항목마다 아래 셋 중 하나로 판정하고, 판정 근거로 지금 파일의 원문을 인용해라.
    해결됨 — 수정 내용이 실물에 있다 (수정된 원문 인용)
    미해결 — 예전 상태 그대로다 (지금 원문 인용)
    근거없음 — 그때 지적 자체가 실물 근거가 없었다 (한 줄 사유)
    요약하지 말고 원문을 붙일 것. 기준선 맨 아래 "다음 점검에서 대조할 것" 항목도 빠짐없이 판정할 것.

    '미해결'이 여러 건이어도 그 자체는 이상이 아니다. 지난 회차에 일부러 이월한 항목이 있다. 기준선에 '수정함' 표시가 있는데 미해결로 나오는 경우만 문제다. 그 경우 저장소 push가 실제로 됐는지부터 확인해라.

(2) 문서와 코드는 서로 다른 속도로 움직인다. 양방향으로 확인해라.
    - 코드를 고치고 문서가 안 따라온 경우 (옵션·등급명·파일 목록이 낡음)
    - 문서만 고치고 코드가 안 따라온 경우 (설명서에만 있는 기능)
    한쪽만 고친 흔적이 있으면 그 자체가 결함이다.

(3) 그다음에 기준선에 없던 신규 항목만 찾아라.

[이월 항목]
이월 목록과 처리 순서는 이 점검표에 적지 않는다. audit/last-audit.md 의 "개선안" 표와 "다음 점검에서 대조할 것" 절을 정본으로 읽어라. 회차마다 바뀌는 정보를 두 곳에 두면 반드시 어긋난다.
다만 아래 두 가지는 성격상 매 회차 판단이 필요하니 잊지 말 것:
월 의존 항목: 1월에만 틀리는 항목이 기준선에 있으면, 오늘이 몇 월인지 보고 시급도를 다시 매겨라. 연말이 가까울수록 우선순위를 올려야 한다.
커플링 항목: 같은 회차에 함께 처리해야 하는 묶음이 기준선에 적혀 있으면, 그 커플링이 지금도 유효한지 실물로 확인해라. 예: 단일 출처 검사를 시트명·컬럼명까지 넓히는 순간 관련 항목이 즉시 FAIL 로 뜨는 관계. 따로 처리하면 push 가 막힌다.

[특히 이런 걸 찾아줘]

■ A. 저장소 SKILL.md ↔ 코드 괴리 (최우선)
SKILL.md에 적힌 명령어·옵션이 실제 스크립트에 존재하는지 (--strict / --no-state / --as-of / --code / --dry-run / --force / --only / --skip-tests / --message / --ref / --token)
SKILL.md의 파일 구성 목록이 저장소 실제 파일과 일치하는지
등급 이름 6종(확인 필요/기한 전/단발·비정기/정상/거래 종료/해결)이 build_report.py의 GRADE_ORDER와 일치하는지
코드에는 있는데 문서 어디에도 없는 옵션이 있는지 (특히 안전장치를 끄는 옵션)
install/SKILL.md 의 부트스트랩 명령이 지금도 그대로 동작하는지

■ B. config 단일 출처가 지켜지는지
check-config.json의 값이 다른 곳에 사본으로 다시 적혀 있는지. 문서 6개(SKILL.md, README.md, install/SKILL.md, references 3종)와 다섯 스크립트, 산출물 A2 안내문구까지 대조:
my_biz.biz_no / name
thresholds: stale_days / monthly_min_months / sporadic_max_months
grace: deadline_day / mode ※ "익월 10일" "10일" 같은 리터럴이 문서에 있는지
colors: 헥스코드 전부
sheets: 시트 이름 4개
input: header_row / tax_marker_column
validate.py 의 단일 출처 검사가 지금도 살아 있는지, 고친 사본을 되살리면 실제로 FAIL 이 뜨는지 반드시 실측할 것. 0건이면 검사가 죽은 것이다. 추가로, config 파일 자체를 지웠을 때 스크립트가 조용히 기본값으로 도는지 아니면 명시적으로 멈추는지도 확인해라. 조용히 도는 쪽이면 결함이다.

■ C. vendors.json ↔ 실제 판정 결과
vendors.json의 거래처가 전부 매트릭스에 행으로 존재하는지 (0건 거래처가 groupby로 사라지지 않는지)
since/until이 실제로 결번 계산에서 빠지는지
cycle 값이 실제 수취 패턴과 어긋난 곳이 있는지
사업자번호 체크섬이 전부 통과하는지
상호가 같은데 사업자번호가 다른 항목이 남아 있는지 (사업자 변경 미정리)
SKILL.md의 vendors.json 예시가 실제 파일 구조·내용과 맞는지

■ D. validate.py가 실제 산출물과 맞는지
0건 매칭인데 PASS가 나는 검사가 있는지 특히 확인:
열을 헤더 '이름'으로 찾는지, 인덱스 하드코딩이 다시 생겼는지
색상 검사가 config의 colors와 따로 놀고 있는지
'미수취=공란' 검사가 None과 빈 문자열을 구분 못 해 무조건 통과하는지
시트 이름 검사가 config의 _comment 키를 다시 읽고 있지 않은지
SKIP으로 빠지는 검사가 몇 개인지, 그 SKIP이 정상인지
'해결' 집계가 등급 열과 상태 열 양쪽을 세는지 (common.is_resolved 를 build_report.py 와 validate.py 가 같이 쓰는지)
검사 대상이 0건일 때 PASS가 아니라 FAIL로 끝나는지. 0건 가드가 없는 검사는 마크업·컬럼명이 바뀌는 순간 조용히 통과한다.

■ E. validate.py가 손대지 않는 구간 ※ 결과는 '개선안'으로 분류할 것
대상외공급자 시트를 검증하는 게 있는지
미수취목록의 등급 분류가 옳은지 검증하는 게 있는지
상계 매칭 결과의 타당성 (쌍이 0개면 의심스러운지)
매트릭스 월별 합 ↔ 원본정제데이터 합 대사가 실제로 도는지
state 비교 결과(신규/계속/해결)가 맞는지 확인하는 검사가 있는지

■ F. 월 경계·기한 처리 (지금이 몇 월인지에 따라 결과가 달라짐)
오늘 기준으로 월 컬럼이 1~현재월까지 나오는지 (고정값이 다시 안 들어갔는지)
'기한 전' 판정이 실행 당월을 빼고 계산되는지
--strict 로 돌리면 '기한 전'이 0건이 되는지
연말/연초 경계: 12월분 기한이 익년 1월 10일로 계산되는지
1월 실행 시 전년 12월분이 대상에 포함되는지 (문서와 코드가 같은 말을 하는지)
A1 제목의 기간 표기가 1월에도 맞는지
부가세 신고기(1기/2기) 밴드가 매트릭스에 제대로 표시되는지
실측할 것: --as-of 2027-01-05 로 한 번 돌려서 1월 경로를 직접 확인. 말로만 "1월에 틀릴 것이다"라고 쓰지 말고, 실제로 그 조건을 만들어서 보여줄 것.

■ G. 저장소 운영 관련
sync.py가 codeload를 쓰는지 (raw로 되돌아가지 않았는지)
push.py의 GROUPS['code'] 가 _scan() 으로 tests/·audit/·install/ 을 자동 포함하는지, 하드코딩 목록으로 되돌아가지 않았는지
저장소 실제 파일과 push 대상 목록을 대조해서 누락이 0인지
push.py의 테스트 게이트가 실제로 작동하는지 (일부러 코드를 깨뜨려 차단되는지 확인)
state 역행 방지 가드가 작동하는지, 그리고 가드가 걸렸을 때 무엇을 확인하고 어떤 조건에서 --force 가 정당한지 문서에 있는지
state/last-run.json의 first_seen이 누적되고 있는지, '해결' 항목이 한 번만 표시되고 사라지는지

■ H. 자동화 가능한 게 더 남았는지 ※ 결과는 전부 '개선안'으로 분류할 것
발급기한 D-day 알림
vendors.json의 cycle이 실제 패턴과 어긋날 때 자동 경고
대상외공급자 중 '추가 권장'을 vendors.json에 반영하는 절차
홈택스 파일 기간이 당해 1/1부터 시작하는지 검사
전년도 12월분(1월 초 수취)이 누락되지 않는지

■ I. 경로·문서 정합성
문서에 적힌 경로·파일명이 실제로 존재하는지
README.md의 명령어가 지금도 동작하는지
README.md·SKILL.md 에 "설치 경로에 직접 쓴다"는 폐기된 지침이 다시 들어가 있지 않은지
validate.py의 check_paths 목록이 실제 파일 구성과 맞는지
xlrd 설치 안내가 이 컨테이너에서 그대로 따라 하면 되는 형태인지

■ J. 데이터가 비거나 1건일 때 죽는 코드
tests/test_edge_cases.py를 돌려보고, 거기서 안 잡는 것도 찾아줘:
세금계산서만 / 계산서만 있을 때
특정 거래처가 마이너스 건만 있을 때 (최종수취일 NaT)
vendors.json이 비었을 때
1월 초 실행(대상 1개월) / 연말 실행(12개월)
홈택스 파일이 0개일 때
같은 구간 파일을 두 번 올렸을 때
state/last-run.json이 손상됐을 때

[판정 기준]
결함으로 올리기 전에 스스로 반증을 한 번 시도해라. "이게 사실은 문제가 아닌 이유"를 찾아보고, 못 찾았을 때만 올려라. 반증 시도 내용은 쓰지 말고 결과만 반영해라.
"특정 조건에서 반드시 틀려진다"고 쓸 거면 그 조건을 말로만 적지 말고 실제로 그 조건을 만들어서 틀려지는 걸 보여줘라. --as-of, 빈 vendors.json, 손상된 state 파일 전부 직접 만들 수 있다. 못 만들었으면 결함이 아니라 개선안이다.
validate.py 검사 전부에 대해 각각 깨뜨려 FAIL이 뜨는지 확인해라. 방법: fixtures로 기준 PASS를 만든 뒤, 각 검사에 대응하는 한 곳만 바꾼다 (색상 헥스 하나, 시트명 한 글자, 미수취 칸에 공백 문자, config 사본 되살리기 등). 하나라도 깨뜨렸는데 PASS가 나오면 그 검사는 죽은 것이고 결함이다. 기준선에 검사별 파괴 방법과 결과를 표로 남겨라. 다음 회차가 그대로 재현할 수 있게.
실측한 것과 코드를 읽고 추론한 것을 구분해라. 결함 표에 [실측]/[추론] 표시를 달고, 추론만으로 올린 항목은 왜 실측하지 못했는지 한 줄로 적어라.

[이 점검표 자체도 점검 대상이다]
이 점검표는 이전 회차에 만든 것이라 틀렸거나 낡았을 수 있다. 마지막에 따로 보고해라.
점검표가 시키지 않았는데 실물을 보다가 확인이 필요했던 것
점검표가 잘못 전제하고 있는 것 (파일 목록, 옵션 이름, 등급 이름, 검사 개수, 이월 항목 판정 등이 지금 실물과 다른 경우)
매 회차 통과만 나서 실효가 없는 검사 항목. 뺄 것을 제안해라. A~J 중에서도 몇 회차 연속 통과만 나온 항목이 있으면 지목해라.
이건 결함·개선안 어디에도 넣지 말고 "점검표 개정안"으로 따로 내라. 개수 제한 없다.

[지적 채택 규칙 — 개수보다 이게 중요하다]
지적하려면 파일 경로 + 줄 번호 + 문제되는 원문을 인용해야 한다. 인용할 수 없으면 지적하지 말고 통과 처리해라. 인용을 못 해서 제외한 항목이 몇 개인지 마지막에 숫자로 알려줘.
설치 경로 사본을 읽고 낸 지적은 무효다. 저장소에서 받은 것만 근거로 쓸 것.
아래 둘을 한 목록에 섞지 마라. 분리해서 따로 내라.
  결함 : 지금 이미 틀렸거나, 특정 조건에서 반드시 틀려지는 것
  개선안 : 있으면 좋은 것 / 자동화 후보 / 검증이 비어 있는 구간
E와 H는 성격상 대부분 개선안이다. 결함 목록에 넣지 마라.
개선안은 최대 5개. 매번 새로 만들어내지 말고, 기준선에 이미 적힌 개선안이 있으면 그걸 다시 쓰고 순위만 갱신해라.

[결과 정리 방식]
결함을 심각도 순으로, 항목마다:
지금 이미 틀렸는지 / 앞으로 틀려질 건지 (틀려진다면 언제)
실측으로 확인한 건지 추론인지
고치면 실제로 뭐가 달라지는지 (가능하면 "확인 필요 N건 → M건" 식으로)
작업 경로를 명시할 것:
  · 코드·설정·문서·SKILL.md·install/SKILL.md·audit/ → push.py --code
  · vendors.json / state → push.py (기본 묶음)
  · install/SKILL.md 를 고쳤으면, push 만으로는 부족하고 내가 Claude 설정에서 스킬을 재업로드해야 한다는 걸 결과에 명시할 것
한 결함이 두 곳에 걸쳐 있으면 양쪽을 다 적어라. 한쪽만 고치면 미완이다.

[마무리 — 기준선 갱신]
진단이 끝나면 저장소의 아래 두 파일을 갱신하고 같은 push.py --code 로 올려라.
audit/last-audit.md — 아래 형식. 이게 기준선 정본이다. 직전 회차 기록은 파일 아래쪽에 "이전 기록" 으로 원문 보존해라.
audit/checklist.md — 이 점검표. 첫 회차면 전문을 새로 저장하고, 이미 있으면 "점검표 개정안"에서 사용자가 채택한 것만 반영한 뒤 머리말의 버전 줄을 갱신해라. 채택 여부를 묻기 전에 고치지 마라.
둘 중 하나만 올리면 다음 회차에 점검표와 기준선이 어긋난다. push.py 의 GROUPS['code'] 가 audit/ 을 자동 포함하는지 먼저 확인하고, 누락되면 그 자체를 결함으로 올려라.
push 후 codeload 로 다시 받아 두 파일 모두 들어갔는지 확인하고, 확인된 뒤에만 완료라고 말해라. 진단 전문을 파일로도 내려줘. 채팅 요약본 말고 파일 자체가 필요하다. 채팅에 요약만 남기면 다음 회차에 절반이 유실된다.
