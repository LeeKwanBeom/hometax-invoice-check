# 정기 점검표 (hometax-invoice-check)

이 파일이 점검 절차의 정본이다. 매 회차 끝에 "점검표 개정안"에서 사용자가 채택한 것만 반영한다. **커밋은 두 번이다**(배민·쿠팡·saero 와 통일, 2026-09-26) — `audit/last-audit.md` 를 먼저(1차, 진단 직후, main), 사용자가 개정안을 채택한 뒤 이 파일을 나중에(2차, 수정 회차, 브랜치 `fix-<날짜>`). 두 파일을 한 커밋에 넣으려 하지 마라 — "채택 여부를 묻기 전에 이 파일을 고치지 마라" 와 동시에 성립하지 않는다. 버전: v7 · 2026-09-27 (7차 수정 회차 — 개정안 1·2·4·6~16 반영, 3 폐기, 5·14후반은 계획)

수정·검증 회차의 지시는 skill-audit 프롬프트 ②(수정 지시)·③(검증) 형식을 그대로 쓴다. 이 파일에 다시 적지 않는다.

**점검 요청 지시**는 skill-audit 프롬프트 ①(진단) 형식을 쓴다. 이 파일은 절차와 기준만 담는다.

[시작 전 확인 ① — 토큰부터 확보한다]

**진단을 시작하기 전에 push 토큰을 먼저 요청해라.** 마무리에 push.py --code 로 두 파일을 올려야 하는데, 진단이 다 끝난 뒤에 요청하면 그 사이 세션이 끊길 때 결과가 통째로 유실된다. 2026-09-07 6차 1차 패스가 실제로 그렇게 끝났다 — 진단과 초안을 다 만들고도 저장소에 아무것도 남지 않았다.

요청 문구에 토큰이 안 보이면 **첫 응답에서** 이렇게 물어라:

> 점검을 시작하겠습니다. 마무리에 기준선과 점검표를 저장소에 올려야 해서 hometax-invoice-check push 토큰(Contents: Read and write)이 필요합니다. 지금 주시면 진단 후 바로 올리고, 없으면 파일로만 드리겠습니다.

토큰 없이 진행하기로 했으면 진단 도중에도 중간 산출물을 파일로 먼저 내려주고 마지막에 다시 알려라. 토큰은 대화에 남으니 작업이 끝나면 폐기하라고 안내할 것.

[시작 전 확인 ② — 업로드 파일의 최종일부터 본다]

**판단 기준은 md5가 아니라 데이터 최종일이다.**
`tests/fixtures/` 의 6개 파일은 사용자의 실제 홈택스 다운로드본을 회귀 테스트용으로
저장소에 넣어둔 것이다. 그래서 사용자가 같은 파일을 다시 올리면 md5가 일치한다.
**md5가 fixtures와 같다고 해서 "실 데이터가 아니다"라고 판정하지 마라. 실 데이터가 맞다.**
2026-09-07 6차에서 실제로 그렇게 잘못 판정했다.

업로드된 xls를 열어 작성일자 컬럼의 min/max를 뽑고, **최종일이 오늘로부터 며칠 전인지**로
아래를 가른다. md5 비교는 참고로만 쓰고, 결과에 쓸 거면 "fixtures와 동일본"이라고만 적어라.

| 데이터 최종일 | 판정 | 어떻게 진행하나 |
|---|---|---|
| 당월 데이터 포함 | 최신 | 그대로 전 항목 실측 |
| 전월까지만 | 한 달 이내 | 진행하되, 아래 ①②는 [추론] |
| 두 달 이상 전 | 낡음 | 진행 전에 최신 파일을 요청 |

실 데이터라도 최종일이 지난 달까지면 다음 두 가지는 실측할 수 없다. [추론]으로 표시해라.
  ① 당월 월 컬럼 생성 — 데이터에 없는 달은 만들어지지 않는다
  ② 당월분 발급기한(익월 10일) 임박 판정
반대로 아래는 최종일과 무관하게 실 데이터면 실측된다. [추론]으로 넘기지 마라.
  홈택스 다운로드 형식(컬럼명·헤더 행·인코딩) · 신규 거래처·사업자번호 변경 ·
  vendors.json 대조 · 체크섬 · 상계 매칭

업로드가 **아예 없으면** fixtures로만 진행하되, 위 ①②를 [추론]으로 표시하고
기준선의 "점검 대상" 줄에 `업로드 없음 — fixtures만 사용` 이라고 남겨라.
어느 경우든 "점검 대상" 줄에 **데이터 최종일과 오늘과의 간격**을 반드시 적어라.
예: `실 데이터 2026-01-01~08-31 (최종일 7일 전), fixtures와 동일본`

없는 데이터를 지어내거나, fixtures 값을 최신 데이터인 것처럼 쓰지 마라.

**fixtures 갱신은 이 점검의 일이 아니다.** fixtures는 기대값이 고정된 회귀 테스트용이라
함부로 갈아끼우면 tests/test_edge_cases.py 가 깨진다. 낡았다고 판단되면 결함이 아니라
개선안으로 올리고, 교체는 사용자 승인 후 별도 회차에 한다.

[운영 조건]
실행 빈도: 월 1~2회. 주로 월초, 전월분 발급기한(익월 10일) 전후
실행자: 나 혼자, 수동 실행
정본은 전부 GitHub 저장소(LeeKwanBeom/hometax-invoice-check, Public)에 있다. push.py --code 로 반영한다.
실사용 회차가 읽는 파일·분량(7차 실측): 설치본 55행 → 저장소 SKILL.md 426행(약 23,000자, view 2회) + audit/last-audit.md(7차 기준 1,300행·80,000자 이상, view 5~6회). 매 회차 재측정해 기준선 효율 표에 적는다(S3 "OPEN.md 로 축소" 는 미채택 상태).
설치본 SKILL.md(/mnt/skills/plugins/hometax-invoice-check/SKILL.md)는 55행짜리 얇은 부트스트랩이다. 저장소를 받아 오라는 안내만 들어 있고 절차·명령어·옵션·등급 이름은 없다. 그 원본은 저장소 install/SKILL.md 다.
설치 경로는 세션마다 패키지에서 다시 풀린다. 쓰기는 되지만 보존되지 않는다. 여기 쓴 건 전부 임시다. 남겨야 할 건 반드시 저장소로 push 할 것. 부트스트랩 문구 자체를 바꾸려면 저장소 install/SKILL.md 를 고쳐 push 한 뒤, 내가 Claude 설정에서 스킬을 재업로드해야 실제로 반영된다.

네가 "못 한다" 또는 "그런 건 없다"고 답할 거면, 그전에 실제로 시도하거나 찾아본 결과를 같이 보여줘. 확인 안 했으면 확인 안 했다고 말해줘.

2. 샘플로 실제 1회 실행해서 산출물 xlsx를 직접 열어볼 것

3. 세 파일이 서로 맞는지 대조할 것
   (a) 지금 이 대화에서 읽히는 설치본 SKILL.md (얇은 부트스트랩)
   (b) 저장소 install/SKILL.md (그 원본)
   (c) 저장소 SKILL.md (실제 설명서 정본)
   (a)와 (b)가 다르면 (b)가 최신이고, 내가 재업로드를 안 한 것이다. md5를 찍어 알려줄 것. (a)에 절차·명령어·옵션·등급 이름이 다시 들어가 있으면 그 자체가 결함이다. 얇게 유지하는 게 이 구조의 핵심이다.

[0단계 — 기준선 대조. 신규 진단보다 이걸 먼저]
1)에서 받은 저장소의 audit/last-audit.md 를 먼저 읽어라. 이게 정본이다. 설치 경로에도 사본이 있을 수 있지만 세션 간 보존이 안 되므로 믿지 마라. 저장소에 없으면 "기준선 파일 없음"이라고 명시하고 (2)로 넘어가라.

(1) 거기 적힌 항목을 지금 실물에서 하나씩 다시 확인해라. 항목마다 아래 셋 중 하나로 판정하고, 판정 근거로 지금 파일의 원문을 인용해라.
    해결됨 — 수정 내용이 실물에 있다 (수정된 원문 인용)
    미해결 — 예전 상태 그대로다 (지금 원문 인용)
    근거없음 — 그때 지적 자체가 실물 근거가 없었다 (한 줄 사유)

    '미해결'이 여러 건이어도 그 자체는 이상이 아니다. 지난 회차에 일부러 이월한 항목이 있다. 기준선에 '수정함' 표시가 있는데 미해결로 나오는 경우만 문제다. 그 경우 저장소 push가 실제로 됐는지부터 확인해라.

(2) 문서와 코드는 서로 다른 속도로 움직인다. 양방향으로 확인해라.
    - 코드를 고치고 문서가 안 따라온 경우 (옵션·등급명·파일 목록이 낡음)
    - 문서만 고치고 코드가 안 따라온 경우 (설명서에만 있는 기능)
    - 직전 회차 후속 조치 표의 문장("무엇을 어떻게 고쳤다")을 코드와 한 번씩 대조 (7차: SKILL.md·push.py 의 "자료에서 채워진다" 가 두 회차 동안 거짓이었다)
    한쪽만 고친 흔적이 있으면 그 자체가 결함이다.

(3) 그다음에 기준선에 없던 신규 항목만 찾아라.

[의도된 동작 — 결함으로 올리지 마라] (2026-09-27 신설)
아래는 사용자가 알고 선택한 것이거나 기준선에 근거가 적힌 것이다. "고치면 좋겠다"는 생각이 들어도 결함이 아니다. 바꾸려면 사용자 승인이 필요하다.
1. `비정기` 라벨은 A 경로(결번·전액취소·수취 0)를 면제하지 않는다 — 수취 월수가 `monthly_min_months` 이상이면 정기 판정(6차 #28 다안, SKILL.md "`비정기` 라벨의 범위").
2. 1월 산출물의 '기한 전' 0건은 정상 구조다(수취 0건 거래처는 C 루프 미진입). 2월도 창이 두 달뿐이라 0 이 정상 — validate 는 기대값(grade_all 재산출)과 정확 일치로 본다(7차).
3. 점검대상 0곳(빈 vendors.json)은 [중단]이 아니라 [경고] — 대상외 목록만 보는 사용이 정당하고, '해결' 둔갑은 listed_ids 가드가 막는다.
4. 직전 달 기한이 지난 뒤(예: 9/27)에는 유예 검사가 기대 0 = 시트 0 으로 PASS 다. 죽은 검사가 아니다.
5. vendors.json 에서 지운 거래처는 '해결' 이 아니다(apply_state listed_ids). 재권유 억제는 `ignore_suppliers` 가 맡고, 판정에는 영향이 없다.
6. `--add-vendor` 와 `--ignore-vendor` 를 같이 주면 [중단] — `--dry-run` 이면 exit 0, 아니면 1.
7. 미래 `until` 은 아직 거래 중 — 결번 판정을 그대로 받는다. 지난 `until` 만 '거래 종료'(common.until_passed 단일 기준).
8. `--strict` 라도 실행 당월은 유예다.
9. state/last-run.json 의 flagged 순서는 등급→최종수취일 정렬이라 최종수취일이 바뀌면 순서만 바뀐 커밋이 생긴다(개선안 3 biz_no 정렬은 이월).
10. 독스트링·주석 속 `익월 10일`·`1/10` 사본 3곳(build_report 8 · check_input 124 · common 82)은 단일 출처 검사가 일부러 뺀다.

  개선안 : 있으면 좋은 것 / 자동화 후보 / 검증이 비어 있는 구간
E와 H는 성격상 대부분 개선안이다. 결함 목록에 넣지 마라.
개선안은 최대 5개. 매번 새로 만들어내지 말고, 기준선에 이미 적힌 개선안이 있으면 그걸 다시 쓰고 순위만 갱신해라.

[결과 정리 방식]
효율 기준선 표를 매 회차 기준선에 넣는다(7차 형식): 실행 이름별 명령 · 벽시계(초) · 도구 호출 수 · 즉석 코드 줄 수 · 산출값, 그리고 실사용 1회(SKILL.md 1~7단계)의 단계별 도구 호출·즉석 코드 표. 속도 후보는 결과 집합 A/B 동일 실측이 있는 것만 올린다.
결함을 심각도 순으로, 항목마다:
지금 이미 틀렸는지 / 앞으로 틀려질 건지 (틀려진다면 언제)
실측으로 확인한 건지 추론인지
고치면 실제로 뭐가 달라지는지 (가능하면 "확인 필요 N건 → M건" 식으로)
작업 경로를 명시할 것:
  · 코드·설정·문서·SKILL.md·install/SKILL.md·audit/ → push.py --code
  · vendors.json / state → push.py (기본 묶음)
  · install/SKILL.md 를 고쳤으면, push 만으로는 부족하고 내가 Claude 설정에서 스킬을 재업로드해야 한다는 걸 결과에 명시할 것
한 결함이 두 곳에 걸쳐 있으면 양쪽을 다 적어라. 한쪽만 고치면 미완이다.

[마무리 — 기준선 갱신]
진단이 끝나면 `audit/last-audit.md` 만 갱신해 **1차 커밋**(`push.py <토큰> --only code`, main)으로 올려라. `audit/checklist.md` 는 사용자가 개정안을 채택한 뒤 **수정 회차에서 2차 커밋**(`--only code --branch fix-<날짜>`)으로 올린다. 커밋은 두 번, 파일은 둘 다 — 한쪽만 갱신하고 회차를 끝내면 다음 회차에 점검표와 기준선이 어긋난다.
audit/last-audit.md — 아래 형식. 이게 기준선 정본이다. 직전 회차 기록은 파일 아래쪽에 "이전 기록" 으로 원문 보존해라.
audit/checklist.md — 이 점검표. 첫 회차면 전문을 새로 저장하고, 이미 있으면 "점검표 개정안"에서 사용자가 채택한 것만 반영한 뒤 머리말의 버전 줄을 갱신해라. 채택 여부를 묻기 전에 고치지 마라.
push.py 의 GROUPS['code'] 가 audit/ 을 자동 포함하는지 먼저 확인하고, 누락되면 그 자체를 결함으로 올려라.
**순서를 지켜라: ① push → ② codeload 재수령 확인 → ③ 그다음에 채팅 보고.** 채팅 보고를 먼저 길게 쓰면 세션이 끊길 때 저장소에 아무것도 남지 않는다(2026-09-07 6차 1차 패스에서 실증). 컨테이너에 남은 파일은 다음 세션에 있을 수도 없을 수도 있으니 믿지 마라.

push 후 codeload(브랜치면 `sync.py --ref refs/heads/<브랜치>`)로 다시 받아 올린 파일이 들어갔는지 확인하고, 확인된 뒤에만 완료라고 말해라. 진단 전문을 파일로도 내려줘. 채팅 요약본 말고 파일 자체가 필요하다. 채팅에 요약만 남기면 다음 회차에 절반이 유실된다.

토큰을 못 받았으면 push를 건너뛰되 두 파일을 반드시 파일로 내려주고 "저장소에 반영되지 않았다"고 명시해라. 완료라고 말하지 마라.
