# 등급 판정 규칙

구현은 `scripts/build_report.py` 의 `grade_all()`.
임계값은 전부 `config/check-config.json` 의 `thresholds` / `grace` 에서 읽는다.
**이 문서에 숫자를 적지 않는다.** 적는 순간 config 가 거짓말이 된다.

## 대전제 — 판정 대상은 데이터가 아니라 vendors.json

업로드 데이터를 `groupby('공급자번호')` 하면 데이터에 있는 공급자만 순회한다.
그러면 **"1월부터 오늘까지 한 건도 없는 거래처"를 원리적으로 못 잡는다.**
가장 중요한 점검 항목이 통째로 빠지는 것이다.

그래서 `build_facts()` 는 `vendors.json` 을 왼쪽에 두고 데이터를 붙인다.

| 방향 | 결과 |
|---|---|
| vendors 에 있고 데이터에 없음 | 매트릭스에 전 칸 공란인 행 → **A. 한 건도 없음** |
| vendors 에 있고 데이터에 있음 | 정상 판정 |
| vendors 에 없고 데이터에 있음 | **대상외공급자** 시트로 |

## 발급기한 유예 (핵심)

세금계산서 발급기한은 **작성월 다음 달의 정해진 날짜**다.
그 날짜는 `config` 의 `grace.deadline_day` 가 유일한 출처다 — 여기 적지 않는다.
월초에 돌리면 전월분이 아직 안 온 게 정상인데, 유예가 없으면
매월 거래처 전부가 "미수취 · 확인 필요"로 잡힌다.

월 1~2회 실행하는 스킬에서 이건 치명적이다. 매번 오탐을 손으로 걸러야 하면
스킬의 의미가 절반이다.

```
mode = auto (기본)
  작성월 M 의 기한 = (M+1)월 deadline_day
  오늘 <= 기한  →  "기한 전"  (미수취 아님, 연파랑)
  오늘 >  기한  →  미수취 확정

mode = strict  (--strict)
  지난 달까지는 유예 없이 전부 미수취로 판정.
  단 **실행 당월은 strict 라도 유예**다. 아직 끝나지 않은 달이라
  미수취로 확정할 근거가 없고, 확정하면 매번 전 거래처가 결번이 된다.
  부가세 신고 직전 최종 점검에 쓴다.
```

### 실행 당월 함정 (두 방향)

실행 당월은 **모드와 무관하게** 유예 상태다(9월 6일에 실행하면 9월분 기한은 익월의 `grace.deadline_day`).
여기서 두 방향으로 틀릴 수 있고, 둘 다 실제로 밟았다.

1. 당월 유예를 **판정에 쓰면** 모든 거래처가 영원히 "기한 전"이 된다.
   그래서 기다리는 중인 달은 `실행 당월을 뺀 유예 월`뿐이다.
   `pending = [m for m in grace if m != as_of.month]`
2. 당월 유예를 **없애면**(strict 를 곧이곧대로 구현하면) 당월이 전 거래처
   결번이 된다. 9/6 실행 기준 확인 필요 6건 → 26건. 그래서 `is_in_grace()`
   는 실행 당월을 mode 보다 먼저 True 로 돌려준다.

| 상황 | 등급 |
|---|---|
| 전월분 못 받음, 기한 아직 안 지남 | 기한 전 |
| 전월분 받음, 당월분만 미도래 | 정상 |
| 전월분 못 받음, 기한 지남 | 확인 필요 |

## A 유형 — 정기 거래처 이상

우선순위 순으로 하나만 붙는다.

| 유형 | 조건 |
|---|---|
| A. 한 건도 없음 | vendors 에 있는데 올해 수취 0건 **이고, 기한이 지난 결번이 하나라도 있음** |
| A. 발행 후 전액취소 | 어떤 달의 건이 전부 상계되어 순액 0 |
| A. 정기 거래처 결번 | `cycle="매월"` 이거나 수취 월수가 임계 이상인데 빈 달이 있음 |

## C 유형 — 최종수취 경과

A 에 잡힌 거래처는 **C 에서 제외한다.** 같은 회사가 두 번 나오면
A 쪽 설명이 더 구체적이라 C 는 정보 없이 자리만 차지한다.

C 안에서 다시 등급을 나눈다. 이 분류가 없으면 "1년에 한 번 거래하는 곳"과
"매월 오다가 끊긴 곳"이 같은 줄에 섞인다.

| 등급 | 조건 | 의미 |
|---|---|---|
| 확인 필요 | 결번이 있고 수취 월수가 단발 기준 초과 | **실제 조치 대상** |
| 기한 전 | 결번 없음 + 유예 중인 달 있음 | 기다리는 중 |
| 단발·비정기 | 수취 월수 ≤ 단발 기준 **또는** cycle 이 `비정기` | 경과일 기준 자체가 무의미 |
| 정상 | 결번 없음 + 유예 월이 실행 당월뿐 | 오탐. 무시 |
| 거래 종료 | vendors 에 `until` 등록됨 | 점검 대상 아님 |

### cycle 라벨은 A 경로를 면제하지 않는다

위 표는 **C 경로(최종수취 후 경과)** 의 등급이다. A 경로(결번·전액취소·수취 0)는
`cycle` 을 보지 않는다. `비정기` 로 등록된 곳이라도 결번이 있고 수취 월수가
`thresholds.monthly_min_months` 이상이면 `확인 필요` 로 올라온다.

의도된 동작이다. 라벨 하나로 정기 판정을 면제하면 오등록 한 건이 진짜 미수취를
통째로 가린다. `check_input.py` 가 "cycle 이 실제 패턴과 어긋남" WARN 으로
불일치를 알려주는 것과 짝을 이룬다 — **입력 검증은 충돌을 알려주고, 판정은
데이터를 믿는다.**

결번이 있는데 등급을 내려야 한다면 라벨이 아니라 `until` / `since` 로
기간을 좁힌다.

## since / until

연중에 거래를 시작·종료한 곳은 그 밖의 달을 결번으로 세지 않는다.
없으면 3월 개시 거래처가 매번 "1·2월 미수취"로 잡힌다.

수취 0건일 때도 이 범위를 먼저 본다. 안 그러면 1월 초 실행에서 전 거래처가
"한 건도 없음"으로 잡히고(1/5 기준 28곳 중 27곳), `until` 이 **작년**인 거래처가
오히려 매번 확인 필요로 올라온다.

```json
{"biz_no": "3458601323", "name": "주식회사올바른푸드",
 "cycle": "매월", "since": "2026-03"}
```

사업자번호가 바뀐 경우(예: 제이푸드)는 구 번호에 `until`, 신 번호에 `since` 를 넣는다.
`check_input.py` 가 "같은 상호인데 사업자번호가 다름" 경고로 이런 케이스를 찾아준다.

## 실행 간 비교

월 1~2회 주기에서 가장 알고 싶은 건 **"지난달 요청한 게 해결됐나"** 다.
`state/last-run.json` 에 `확인 필요` 목록과 `first_seen` 을 남긴다.

| 상태 | 의미 |
|---|---|
| 신규 | 이번에 처음 잡힘 |
| 계속 (N개월) | 지난번에도 잡혔고 아직 미해결 |
| 해결 | 지난번 잡혔는데 이번엔 정상. **한 번만 표시하고 다음 실행부터 사라진다** |

`first_seen` 이 핵심이다. "3개월째 미해결"이 보이면 우선순위가 달라진다.

## 부가세 신고기

매트릭스 월 헤더 위에 신고기 밴드를 표시한다. 어느 달이 몇 기인지는
`config` 의 `vat_period.periods` 가 유일한 출처다.

1월·7월 초 실행이 각 기 확정 직전 마지막 점검이므로, 그때는 `--strict` 로
유예 없이 한 번 더 돌려 직전 기를 확정 판정하는 것을 권한다.
**1월 실행에는 전년 12월이 점검 기간에 자동으로 포함된다.**
12월분 기한이 익년 1월이라, 넣지 않으면 12월은 영영 판정되지 않는다.
